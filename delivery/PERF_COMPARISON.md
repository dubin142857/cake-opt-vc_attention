# 性能对照 — 本交付 vs 官方 MindIE Laser Attention

> 面向验收的一份独立对照。所有数字均为本机实测，测量脚本与原始 json 见文末「复现」。
> 不利的结果同样列出。

## 一句话

在本机 Ascend 910B2、形状 `[1, 28, 37741, 128]` BF16 上，本交付相对贵方基线
`9e3a550` 把核心耗时降低 **74.4%**（`control`）/ **75.8%**（`expcast`）。
但把官方 **MindIE Laser Attention** 从上游源码在同一台机器上编译后直接对测，
**Laser 仍比本交付快 3.0 倍，且对 FP32 稠密参考的相对 RMSE 小约 16 倍。**

两项必须同时看。只报其中一项都会给出相反的印象。

## 一、测量条件

| 项 | 取值 |
| --- | --- |
| 设备 | Ascend 910B2，单卡，`ASCEND_RT_VISIBLE_DEVICES` 指定非 0 号物理卡 |
| 形状 | `[B=1, N=37741, H=28, D=128]`，自注意力，BF16 |
| CANN / torch_npu | 9.0.0 / 2.9.0 |
| 计时口径 | 只计原生核心调用，`prepare()` 与预处理在计时之外 |
| Laser 来源 | 上游 `github.com/Ascend/MindIE-SD` 提交 `71098c20`，本机从源码编译 |
| 本交付来源 | 分支 `h26-bitdecode`，内核止于 `53ec7af`，产物 sha256 `3494c48d2ce2b73e…` |
| 测量日期 | 2026-10-28（两者在数分钟内先后测得，机器状态相同） |

## 二、本交付 vs 贵方基线（同一实现路线，可直接比）

`tile_m=64`，只计 `run_prepared()` 的原生核心调用：

| | `control_m64` | `expcast_m64` |
| --- | ---: | ---: |
| 贵方基线 `9e3a550` | 1102.63 ms | 1234.05 ms |
| 本交付（内核 `0979605`） | **283.38 ms** | **298.23 ms** |
| 降幅（两会话均值） | **−74.36%** | **−75.79%** |

说明：表中 ms 为其中一个会话的值，降幅为**两个独立会话的均值**，两者不是互相除出来的。
逐会话降幅为 −74.30% / −74.42%（`control`）与 −75.83% / −75.75%（`expcast`），
跨会话极差 0.12% / 0.08%。基线为同次重新构建后实测，不是引用历史数字。

## 三、本交付 vs 官方 MindIE Laser Attention（不同数值契约）

同机、同卡、同形状：

| 实现 | 核心耗时 | `dense_fp32` 相对 RMSE |
| --- | ---: | ---: |
| **官方 Laser**（FP16，不量化） | **95.30 ms** | **0.191 %** |
| 同机 CANN `npu_fusion_attention` | 142 ms | 0.234 % |
| 本交付 `control`（`tile_m=64`） | 285.46 ms | 2.98 % |
| 本交付 `expcast`（`tile_m=64`） | 299.89 ms | 4.36 % |

**耗时**：Laser 快 **3.0 倍**。
**精度**：Laser 的相对 RMSE 小约 **16 倍**。

★ 精度这一项与 tile 切分、指令条数、流水重叠度**都无关**，它来自数值契约本身：
Laser 走 FP16 不量化，本交付走 INT8 QK + E4M3 V 的量化路线。换言之，
继续在本路线上做性能优化**不会**缩小这个精度差距。

而能把本交付耗时明显压低的那条杠杆（QK 直出 FP16，存档见 `OPTIONAL_FP16_S.md`）
恰好被精度闸拦着：它的 `decoded_reference` 相对误差 1.1089%，超过 1% 的验收门限，
此前已被否决过一次。

## 四、贵方此前记录的 Laser 数（A3，本机未复现）

列在这里是为了让两侧口径能对上，**不参与排名**——设备与运行条件不同：

| 记录项 | full API | native API | 相对 dense RMSE |
| --- | ---: | ---: | ---: |
| `original_laser` | 85.509 ms | 81.2776 ms | 0.190947 % |
| `vector_pv_prefetch`（稳定线） | 83.6454 ms | 79.1086 ms | 1.365174 % |
| 新 provider 开启 FP16 ExpCast | 123.1336 ms | — | 2.282386 % |

★ **一条强交叉验证**：贵方记录的 `original_laser` 相对 RMSE 是 **0.190947%**，
本机从源码编译后实测也是 **0.190947%**，六位小数完全一致。这说明本次在本机编译的
确实是同一实现，Laser 一侧的对比数据可信。耗时 85.5 ms（A3）对 96.37 ms（本机 A2
910B2），设备不同，量级一致。

★ 另需指出：上表第三行「新 provider 开启 FP16 ExpCast」(123.13 ms / 2.28%) 是贵方
当时**已否决**的候选，理由记为「0/9 轮更快且误差增大」。本交付当前的位置
（285.46 ms / 2.98%）在同一判断标准下方向相同。

## 五、口径边界

- 两侧精度是**同一个字段名、同一种口径**（对 FP32 稠密参考的 `relative_rmse`），
  单位已逐项核对（Laser 报表中的 `dense RMSE %` 即 json 内 `relative_rmse × 100`）。
- Laser 的精度采样覆盖至多 32 个 query 行（其脚本自述），本交付为长形状全量。
  但两者相差一个量级以上，远超采样差异所能解释。
- 计时协议不同：Laser 为进程分组同步计时，本交付为 `bench_one.py` 的重复中位，
  两者都排除预处理。3.0 倍的差距同样远超协议差异。
- 同机 CANN 融合算子的 142 ms 只作背景参照，**不是加速比**——它与本交付是两个
  不同数值契约的算子。
- 未跑 `qkv_int8_e4m3_expcast` 等变体。那回答的是「把本路线搬进 Laser 框架会怎样」，
  与「本交付 vs Laser」不是同一个问题。

## 六、关于「本设计还能压到多低」

本交付 `expcast` 臂当前每 tile 的 AIV 向量段耗时 2.03 us，乘 101873 个 tile 约 **207 ms**。
这个数的准确含义是：**任何只改跨核协议（同步、重叠、流水）的改动都降不到它以下。**

**它不是本设计的硬下界。** 它锁定的是当前的 AIV 指令条数，而那不是硬件地板——
同类论证此前对 2.4481 us/tile 说过一次，随后用位运算替换 Gather 就把它降到 2.03
（−17%，且未改动任何跨核协议）。同机 CANN 融合算子是一个现成的反例：它做的算术
**更多**（cube 忙时 82.2 ms 对本交付 50.8 ms），却只用 142 ms，差距在流水重叠度
（2.46 对 1.51）。

即便乐观地按 207 ms 计，相对 Laser 的 95.30 ms 仍慢 2.2 倍，且精度差距不变。

（此前文档中出现过 193.2 / 161 / 129 ms 三个更低的下界估计，**已作废**：
它们建立在「耗时由搬运字节数决定」的模型上，而后续实测用相同字节量测出一倍耗时差，
推翻了该模型。请勿再引用。）

## 七、一处必须告知的正确性缺陷

与性能无关，但影响贵方手上的版本，一并说明。

2026-10-28 定位并修复了一个竞态：同一 AIC 上的两个 `MatmulImpl`（QK 与 PV）共用物理
L0A/L0B 与 `M_MTE1` 事件号。它在 **`tile_m=32`**（即 `run_prepared()` / `attention()`
的**默认值**）长形状上导致结果不确定——同一输入连调 24 次，23 次结果不同；
512×4 小形状上偶发 aicore 507015。

这是**最初的 Ascend 移植（`da6026b`）就带的结构**，两个实例的声明此后从未改动；
本次优化把 AIV 侧提速，才把触发率从 9% 推到 100%。
**因此 h11 时期交付的版本大概率同样带这个缺陷**（未实测）。

修复 `53ec7af`：在两个 matmul 的发射点之间串行一次。`tile_m=64` 输出与修复前**逐位相同**
（只改时序不改值），代价 `tile_m=64` 上 +1.14% / +0.41%，`tile_m=32` 上无代价。
修复后 `tile_m=32` 由 100% 发作降到 0/47（两个独立会话），24 个用例全过。

本文第二、三节的数字全部在 `tile_m=64` 上测，不受此缺陷影响。

## 八、结论

1. 相对贵方基线，本交付的优化是实在的：核心耗时降低 74.4%，两个独立会话复现，极差 0.12%。
2. 但在同机同形状的直接对照下，官方 Laser 快 3.0 倍、精度好约 16 倍。
   精度差距来自量化契约，继续优化性能不会缩小它。
3. 据此，**是否继续在本量化路线上投入，建议由贵方重新判断**。我方不单方面推进。
4. 竞态缺陷已修复并验证；建议贵方核对手上版本是否受影响。

## 九、复现

```bash

python3 scripts/build_mindie_laser_local.py  --cann-root /usr/local/Ascend/cann-9.0.0 --soc ascend910b --jobs 1
python3 scripts/build_mindie_laser_bridge.py --source-dir build/mindie_laser_source --cann-root /usr/local/Ascend/cann-9.0.0 --jobs 16
```
