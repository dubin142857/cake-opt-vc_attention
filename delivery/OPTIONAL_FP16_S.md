# 可选级存档：QK 经 fixpipe 反量化直出 fp16

> **本级不在交付内。** 它在原验收判据下**不通过**，故单独存档，由甲方决定是否采纳。
> 交付内容见本目录 `README.md`，止于五处不碰数值路径的改动。

分支 `h14-fp16s-on-h11b`，提交 `78286b4`，产物 `5d3e1d64ae9ff3e25f2f`。

## 做了什么

把 QK 的 matmul 输出由 int32 改为 fp16，S 的 GM 回写字节减半。

int8×int8 的累加器天然是 int32（d=128 时内积最大 `128×127×127 = 2064512`，
而 fp16 上限只有 65504，直接收窄会溢出）。可行的唯一途径是让 **fixpipe 在写出时
先施加反量化、再收窄**——出来的是真实的 score（量级 O(10)），那个装得进 fp16。

实现上：`c1Type` 由 `int32_t` 改为 `half`，并用 `SetQuantVector` 提供按 N 通道的
反量化系数（承载 `k_scale * scale`）。`q_scale` 沿 M 变化而 fixpipe 的反量化向量
只能按 N 通道给出，故仍由 AIV 以单标量施加——每个 AIV 子块恰好覆盖一个 Q 量化块。

判据依据：`quant_processor_utils.h:47` 的
`IsSameTypeV<L0cT, int32_t> && IsTypeOneOfV<CType, half, int8_t, uint8_t>`，
不在任何架构门控内；int8 输入的 `L0cT` 正是 `int32_t`。
旁证：CANN 自带的 `prompt_flash_attention` 在 `mmInputType == int8_t` 时
调用 `mm.SetQuantScalar`。

**附带好处**：反量化搬到 fixpipe 后，K 的 scale 乘法从 AIV 挪走——原先要按列分段
做 `Muls`（每个 K 量化块一次），现在只剩一次整 tile 的标量 `Muls` 补 Q 的 scale。

## 收益（abgate 的 ABBA 协议 8 轮，三条判据全过）

收益**不可叠加**，取决于叠在哪一级上：

| 基座 | 口径 | 前 → 后 | 省 | 效应 |
| --- | --- | ---: | ---: | ---: |
| h10 | `control_m64` | 465.01 → 443.57 ms | 21.44 ms | −4.24% |
| h10 | `expcast_m64` | 588.17 → 564.71 ms | 23.47 ms | −3.09% |
| **h11b（交付版）** | `control_m64` | 330.21 → 323.29 ms | **6.92 ms** | **−1.96%** |
| **h11b（交付版）** | `expcast_m64` | 354.01 → 333.29 ms | **20.72 ms** | **−5.82%** |

叠在交付版上对原始基线的累计：`control` −70.7%，`expcast` −72.9%
（交付版本身为 −70.0% / −71.2%）。

`control` 路径的绝对节省由 21.44 ms 掉到 6.92 ms，因为上一级（AIV 推迟累加）
已经把 AIV 等 PV 的时间填上，fixpipe 省下的那部分不再暴露在关键路径上。

机理实测：`aic_fixpipe` 在元素数不变、只有字节数减半的对照下降 **13.7%**。
★注意它**不是按字节线性的**——纯字节模型会预测 −33%。

## 代价

### 1. 这是论文未要求的精度收窄

论文的 CUDA 实现用 **fp32** 的 C 矩阵（`csrc/kernels.cu:332` 的
`CUDA_R_32F` 布局与 `CUBLAS_COMPUTE_32F`，核内 `kernels.cu:212` 为 `float score`）；
甲方基线用 **int32**。`PAPER_ALIGNMENT.md` 的对照表只规定 Q/K/V 的量化粒度与
ExpCast 的编码方式，**对 S 的存储宽度没有要求**——它是中间量。

即：本级是实现侧引入的收窄，不是论文契约的一部分。

### 2. 它不通过原验收判据

`decoded_reference`（与同契约 oracle 的相对 RMSE，闸门 1%）：

| | control | expcast |
| --- | ---: | ---: |
| 交付版（int32 S） | 0.000068 | 0.000043 |
| 本级（fp16 S） | 0.001956 | **0.011089** ← 超 1% |

**原因不是实现缺陷。** 定位链（每一环有实测）：

- S 本身吻合：用 V=单位阵提取内核实际算出的 S 逐元素比对，单 tile 下与 oracle 的
  差分 RMS 仅 3.6e-4（相对 S 的跨度 5.5 是 6.6e-5），与 fp16 舍入噪声一致；
- 失配不随 tile 数累积：keys 由 256 到 32768（1 到 128 个 tile）全程平坦；
- 机理是 **ExpCast 的 E4M3 硬量化放大 S 的末位扰动**：E4M3 只有 121 个离散码、
  相邻步长 6.2%，一个 fp16 ulp 的扰动使 **1.662% 的码跳变**，输出相对 RMSE 被放大
  **11.3 倍**（半个 ulp 时 16.8 倍）；普通 `exp` 是光滑函数，几乎不受影响。

数据自身也佐证：control 路径（光滑）由 6.8e-5 涨到 1.956e-3 是 29 倍，
expcast 路径由 4.3e-5 涨到 1.1089e-2 是 258 倍，**两者之比 8.9 倍**，
与独立测得的放大倍数吻合。

已逐一排除的其它解释：舍入次数（fp32 两次 / fp64 一次 / 完全不舍入三者几乎相同）、
按通道反量化向量的编码（`SetQuantScalar` 与 `SetQuantVector` 给出完全相同的数字）、
反量化系数的尾数截断（scale 取 2 的幂后失配只降到 0.001498 而非消失）、
尾数受限的中间表示（中间尾数降到 11/10/9/8/7 位时失配单调变差，fp32 中间为最优拟合）。

结论：该闸门在 fp16-S 契约下**实质要求两条独立的 fp16 舍入路径逐位一致**——
硬件 fixpipe 的舍入与 torch 的 `.half()` 偶有末位分歧，而 ExpCast 恰好放大它。
这不是实现质量问题。

### 3. 对真实 attention 的质量影响很小但不是零

9 个点（keys 1024/2048/4096 × 种子 1/2/3，每点 256 个 query 行）对真实 dense attention：

| | 交付版 | 本级 | 差 |
| --- | ---: | ---: | ---: |
| `expcast` | 0.043676 | 0.043786 | 误差预算的 **+0.25%**（9/9 点一致略差） |
| `control` | 0.029440 | 0.029444 | +0.01% |

该误差预算由 E4M3 的 ExpCast 量化主导（4.37%）。

## 其余验收（均通过）

12 个形状组合全过；141 用例 `status=passed`，`decoded_reference` 136 点最大
0.009590、0 个超 1%（小形状下不触发长形状的累积效应）；6 组形状各连发 8 次
全部 8/8 逐位相同。

## 若要采纳

需要同时接受两件事：论文未要求的精度收窄，以及 `decoded_reference` 对 expcast
路径的判据调整。曾评估过的调整方案是「expcast 守相对 control 的放大倍数 ≤ 15」
（机理给出 11.3–16.8 倍，本级实测 5.7 倍）外加 `dense_fp32` 对既有基线的回归检查。
该方案的**已知代价**：若某缺陷只影响 expcast 路径、把 `decoded_reference` 从 0.011
推到 0.02（放大倍数 10，仍在 15 内），新判据抓不住，而原判据能；
`dense_fp32` 的回归检查是否一定兜得住该情形，未经验证。
